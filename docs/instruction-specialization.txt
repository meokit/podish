Instruction specialization declarations
======================================

instruction_catalog.json is the source for decoder fallbacks, specialization
selectors, named kernel bindings and selection of operations for the LLVM
prototype. CMake runs scripts/gen_instruction_catalog.py to generate the
encoding traits, native registration table and named wrappers. Execution
kernels live in ops/*_impl.h.

Declaring a variant
-------------------
Each variants row has a logic name, an encoding family, a spec object and a
priority. For example:

  {"logic": "OpGroup1_EvIb_Add_32_NoFlags_Eax", "family": "Group1_EvIb_Add",
   "spec": {"width": ["W32"], "regForm": [], "dst": ["Eax"], "flags": ["Dead"]},
   "priority": 2}

The family supplies the handler index, opcode extension and operand roles.
The generator lowers the spec object to a structural C++ Spec value.
DeclareVariant checks the spec and derives the decoder criteria. The bucket
sort uses descending specificity followed by ascending priority. The optional
fusion_parent field permits a bounded expansion of an existing fusion.

A binding row supplies the name of the logic entry, its kernel and template
arguments. Every bound logic entry has its own name and remains callable from
generated fusion code.

Typed facts
-----------
- Width and r/m form are independent. Register form does not imply 32 bits.
- dst/src are semantic operands. Family layout maps them onto ModRM.reg or
  ModRM.rm; an opcode extension is not a GPR operand.
- Vector operands require a bank-specific policy; SIMD prefix families do not
  accept a GPR identity as a vector-register label.
- Fixed byte encodings accept EAX..EBX plus ByteLane::Low/High. For example,
  dst8(Gpr::Eax, ByteLane::High) denotes AH, not ESP.
- Dynamic base/index means unresolved; Absent means known to be missing.
- Segment::Default means no segment override. It still uses the architectural
  DS/SS base, including non-flat segment bases.
- Fixed-width encodings, scalar operand-size prefixes and SIMD mandatory
  prefixes have separate width rules. mandatory(P66/F2/F3) does not stand for
  an integer operand width.
- Flags::Live/Dead retain the original strict liveness matching. Flags::Any
  explicitly permits both and requires a body valid in both situations.
  Dead flags never remove ADC/SBB's input CF dependency.
- Inconsistent or unsupported facts fail compile-time validation. The existing
  selected set remains unchanged except for removing 32 identical MOV entries.

The kernel-side types in instruction_kernel_spec.h include OpsizeSpec,
AddrModeSpec, FlagsSpec, RmOperandSpec and GroupOpSpec. Their Dynamic cases
use decoded inputs or preserve the generic flags behavior. The common
OperandSpec policies bind slot count and trained operands. Opcode and
mandatory-prefix semantics come from the architectural catalog.
OperandSpec::Profile binds exact decoded operands for baked fusions.

RegisterSpecializedHandler can publish a rule after initialization. A runtime
rule affects future decodes, and the caller owns the lifetime of its code.
The catalog exposes build-time metadata independently of runtime registration.

Dynamic operand templates
-------------------------
FIBERCPU_DYNAMIC_OPERAND_PLAN_FILE selects profiled operand shapes to generate
from the same LLVM kernels and operand rules used by the block JIT. At build
time LLVM specializes, inlines and compiles each handler to an ARM64 object.
The packer extracts machine-code templates, immediate patches and relocation
metadata. The interpreter only needs those artifacts when online JIT is off.
The build requires native macOS arm64 and matching upstream Clang and LLVM
major versions (21 or newer). Set FIBERCPU_DYNAMIC_SPECIALIZATION=0 to disable
runtime materialization.

LLVM block JIT
--------------
FIBERCPU_ENABLE_LLVM_JIT enables the ORC block compiler on macOS arm64.
Set FIBERCPU_LLVM_JIT=1 for exact operands or =generic for generic LLVM kernels.
The default runtime mode is off.

FIBERCPU_LLVM_JIT_HOT_THRESHOLD sets the block entry count before compiling the
published block, including entries reached by threaded links. The default is
64. Promotion re-decodes the published slots with architectural fallback
handlers and uses their operands to specialize LLVM bitcode. The compiled
prefix retains those generic scalar handlers for memory replay.
The remaining slots keep their native lowering. If the prefix reaches the
sentinel, the compiler inlines the normal OpExitBlock semantics.

Online JIT snapshots the published instruction bytes on the VM thread.
Two workers re-decode, optimize and emit objects concurrently by default.
The guest executes the native handlers until a completed block can be
installed at a dispatch boundary. A cache reset cancels pending publication
and a block invalidation rejects results for its previous revision.
FIBERCPU_LLVM_JIT_WORKERS selects 0–8 workers. Set it to 0 for synchronous
promotion. Profile collection records block recipes synchronously.

The asynchronous scheduler samples recent block visits from the existing
entry countdown. It ranks a bounded candidate list by visit rate, expected
dispatch savings over the installed static handlers, and estimated work.
Older candidates age out before their instructions are copied. The shared
pool allows an initial burst of 64 ms of compiler CPU and replenishes the
budget at half of the configured workers' CPU capacity. Completed jobs
reconcile their reservations with measured thread CPU time.

FIBERCPU_LLVM_JIT_SCHEDULER_TRACE=/path/to/trace.csv
captures accepted submissions, queue and compiler timings, and block visits
between JIT installation and invalidation or cache retirement.

Podish passes CPU options to libfibercpu
----------------------------------------
Use -XX:Name=Value or repeat --cpu-opt Name=Value before the guest command.

  podish run -XX:JitMode=exact -XX:JitHotThreshold=128 -XX:JitWorkers=2 \
    '-XX:LlvmPipeline=default<O1>' -XX:BlockCacheSize=512m \
    -XX:JitArenaSize=128m IMAGE COMMAND

Run saves these strings in the container spec. Start appends its options,
and the last value for each name wins. Podish forwards the values as UTF-8.
libfibercpu validates the full batch before applying it and reports errors
for unknown names, invalid values or unavailable build features.

BlockCacheSize defaults to 64 MiB per MMU and is inherited by forked MMUs.
JitArenaSize defaults to 128 MiB per host process and is rounded up to a
host page. LLVM builds accept up to 2 GiB to keep code and data within
the AArch64 Page21 relocation range. Sizes accept bytes or binary suffixes
such as k, m and g.
--block-cache-size and --jit-arena-size are legacy CLI shorthands. A saved
spec with both old JIT limits migrates to the smaller nonzero size.

JitMode selects off, exact, generic or profile for the run. JitHotThreshold
sets the entry count before an asynchronous block is considered for ranking
(1 through 65535). Synchronous compilation and profiling use it as the
admission count. These options override the equivalent Host environment
settings. JitWorkers accepts 0 through 8.
LlvmPipeline accepts an LLVM IR optimization level (O0, O1, O2, O3, Os, Oz)
or a textual pass pipeline. The default is O2 with dead template definitions
removed early online. LlvmFoldOperandLoads=on enables extra folding of
decoded operand reads after LLVM inlines the exact block template. The
default is off. Use FIBERCPU_LLVM_FOLD_OPERAND_LOADS=1 to set the process
default or to enable the same pass in fibercpu_llvm_cache when generating
a linked cache. The pass uses the packed layout of single- and two-slot
instructions and keeps branch targets, link offsets and mutable bits live.
The existing exact-operand argument bindings apply in both settings.

After inlining and optimization, the online compiler and linked cache builder
trace single-bit tests in the block's LLVM SSA. Proven predicates can feed
consumers such as Jcc and CMOVcc directly. Packed flags remain available at
block exits and memory replay, and the pass leaves unproven reads in place.

  podish run -XX:JitMode=exact -XX:LlvmFoldOperandLoads=on IMAGE COMMAND

Worker count, pipeline, operand load folding and JIT arena capacity are
shared by the host process. Once initialized, an explicit conflicting value
fails. A run with no override uses the shared setting.

Native hosts use X86_CreateRun to validate a batch of NUL-terminated UTF-8
Name=Value entries and X86_CreateForRun to create its CPU states. The states
and their cloned MMUs retain the options. Call X86_FinishRun after its CPUs
stop, then X86_DestroyRun to release the configuration. Legacy native
callers can still set cache budgets with X86_ConfigureCodeCache.

The arena charges reserved executable slabs, the dynamic instruction
specialization region and page-rounded LLVM data. It reserves two address
ranges at initialization, each sized to the budget, with one shared limit on
allocations. LLVM packs code into 256 KiB slabs in the MAP_JIT range and
allocates data pages in the nearby non-executable range. JITLink relocates
each block at its final addresses, applies the data permissions, copies the
code and invalidates the instruction cache before publishing the entry.

Online LLVM blocks share one process-wide cache generation. Each successful
link transfers its ORC resources to the generation tracker. The generation
keeps compiled recipes reusable across ordinary MMU cache resets. If a new
block would exceed the arena budget and could fit in a fresh generation,
running MMUs leave their block chains at a dispatch boundary. The cache
discards that generation and releases its slab and data reservations after
active execution and linking are quiescent. Each MMU drops its old decoded
blocks before re-entering execution. In-flight compiles from an old generation
cannot link or publish into the next one. Destroying the last MMU also
releases the generation. Blocks that fail linking keep their native entry.
The linker periodically removes unreferenced symbols from failed links.

Native stats report the total shared budget charge in jit_arena_used_bytes
and the LLVM portion in llvm_code_cache_bytes. The configured capacity is
jit_arena_capacity_bytes. A zero capacity means the arena has yet to be
mapped. X86_GetLLVMJitBlockCount counts online block materializations.

Linked LLVM block cache
-----------------------
Use an LLVM-enabled producer to collect exact block recipes with an
execution weight. The workload uses native dispatch during collection.

  podish run -XX:JitMode=profile -XX:JitHotThreshold=64 \
    -XX:WeightedProfilePath=/tmp/blocks.profile IMAGE COMMAND

An explicit profile path selects profile mode when JitMode is omitted.
A relative path is resolved from the host working directory at launch.
Use WeightedProfilePath= to clear an inherited path when changing modes.
Each eligible recipe admitted at the hot threshold records its total
block entries, including earlier entries before admission. Counts for
the same recipe are merged across guest MMUs and cache resets in the
same run. Podish finalizes the run after the scheduler returns and native
code writes the profile atomically.

WeightedProfileSamePage=on also samples the valid registered blocks starting
in the hot block's guest page in the same MMU when the threshold is reached.
Recipe generation runs at the dispatch boundary. Members that can be
compiled use the same entry counters, with an export weight of one for
recipes that were registered but never entered. The offline tool still
compiles independent blocks.

A block key contains the exit and ordered catalog-assigned operation IDs.
Exact keys include decoded operand shapes and the relative guest EIP
layout, including discontinuities introduced by concatenation. Compiled
handlers derive their guest EIP base from the installed block, so identical
recipes can share code across guest addresses. The profile and linked bundle
must be regenerated for the relative EIP key format. LLVM
templates are indexed by the same IDs. Weighted profiles store each key's
64-bit entry count in little-endian order before its encoded record.
The legacy unweighted format, produced using FIBERCPU_LLVM_JIT=profile
and FIBERCPU_LLVM_JIT_PROFILE, also works with the offline tool. Profiles
validate embedded bitcode, LLVM version and host CPU target. Regenerate
profiles and linked bundles when changing the producer.

  <producer>/fibercpu_llvm_cache --linked /tmp/blocks.profile blocks.linked \
    --top 512 --llvm-opt-level O2

The offline tool sorts weighted recipes by descending entry count.
--top limits the number of emitted objects. --llvm-opt-level and
--llvm-pass-pipeline are mutually exclusive.

Configure the interpreter using the same sources, compiler, target and VM
layout settings as the producer, with the linked bundle as a build input.

  cmake -S libfibercpu -B <consumer> -DFIBERCPU_ENABLE_LLVM_JIT=OFF \
    -DFIBERCPU_LINKED_BLOCK_CACHE_FILE=/absolute/path/blocks.linked
  cmake --build <consumer>

The C++ table and its objects link into libfibercpu. This build needs Python
and an upstream Clang toolchain on native macOS ARM64. An LLVM-disabled
build runs without the LLVM libraries. The linked handlers use the library's
normal executable pages and receive their relocations from the platform
linker. Use trusted build-time bundles. CMake checks the ABI fingerprint,
and a different host CPU falls back to native dispatch.

The linked cache is enabled at runtime by default when built in.
FIBERCPU_LINKED_BLOCK_CACHE=0 disables its use independently of
FIBERCPU_LLVM_JIT. The linked cache alone tries each decoded block on its first
entry and falls back to native dispatch on a miss. When online JIT is also
enabled, the online hot threshold controls promotion. The linked lookup runs
first, and misses go to the online compiler. X86_GetLinkedBlockHitCount counts
linked block entry installations. Linked handlers persist for the lifetime of the
library and use no per-MMU JIT allocation budget.

Tool metadata
-------------
X86_GetInstructionVariantCount/GetInstructionVariant expose the architectural
catalog with normalized encodings and stable variant keys. X86_GetTrainingHandlerId
canonicalizes native and baked handlers to structured training IDs. Use the
handler-reflection API to inspect individual native symbols within the current
process. The baked-fusion generator reads the numerical sequences from its
profile manifest.

Migration evidence (Apple M5 Max, macOS ARM64)
--------------------------------------------
The pre-refactor registry was captured before conversion. Every one of its 503
unique selected variants and 411 final fallbacks retains its exact normalized
constraints and legacy precedence. The regression fixture records this baseline.
32 duplicate MOV rows selected the same logic under identical constraints and
were merged. Reflection retains 943 handler entries with the default 71 fused
sequences, and 872 when generated fusion is disabled.

Final CPU suite: 3145 passed with fusion ON and 3145 passed with fusion OFF,
including 32 exhaustive cases and four new catalog regression tests.
PerfTools: 29 passed, including byte-for-byte regeneration of the checked-in
fusion source, metadata-driven expansion and stale-snapshot rejection.
Python reflection tooling: 5 passed. Compile-time contract checks also run in
all native builds.

Serial rotating GCC CoreMark comparison, fixed 60000 iterations, three rounds:
  old registry median 3265.306122
  unified registry   3284.971257  (+0.602%)
All six CRC/timing validations passed. Same managed CLI, rootfs, guest binary,
compiler and fusion table; only the native library changes. No concurrent build
or profile ran during measurement.
Two-round independent throughput comparison (all 12 output checks passed):
  GNU gzip       -0.285%
  GNU SHA256     +1.144%
  Zig CoreMark   +0.038%
These are short comparisons, not statistical confidence bounds or new speedups.
Executable __text: 688372 -> 651212 bytes (-5.398%). Metadata adds read-only
storage; total library size is not a substitute for executable-code size.
