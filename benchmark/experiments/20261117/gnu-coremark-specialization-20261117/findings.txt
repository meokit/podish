GNU tools + CoreMark: ARM64 manual specialization and fusion baking, 2026-11-17

结论：保留特化，通过生成时展开安全的语义特化家族修复精确融合匹配。
SHA256 吞吐 +24.55%，10 例等权几何平均 +2.65%；CoreMark 与其余 GNU 工具主要是小幅波动。
当前代码已整理到工作区，未自动提交或推送。

环境与方法
Apple M5 Max / macOS ARM64；宿主 Apple Clang 17 Release + ThinLTO。preserve_none ON，运行时计数型 profile OFF。
基线提交：2efc85b6f83fb0e58a20917e5fa81fcf68c208f1
GNU tar 1.35、gzip 1.13、sed 4.9、grep 3.11、coreutils 9.5，musl i386，来自 prepare_gnu.py 的固定锁定软件包。
CoreMark 上游 1f483d5b8316753a742cbf5590caf5bd0a4e4777；GCC 15.2.0 -O2 和 Zig 0.15.2 / Clang 20.1.8 -O3 i686 静态版本。
两种 CoreMark 都在相同完整 rootfs 中执行，自动校准 >= 10 秒。所有 90 次运行均校验输出/CRC。
8 个 GNU 工作负载 + 2 种 CoreMark；3 轮，每轮轮换工作负载/版本顺序；单进程串行计时。
GNU 时间取宿主 BEGIN/END 标记，含 bash 循环和命令 fork/exec，排除 CLI 启动。每例约 4 秒。
单独采样，不与计时或编译重叠；xctrace Time Profiler，按相位分组并排除每相位前 150ms。
符号占比为 libfibercpu 内样本占比，不能当成完整进程时间；两次 profile 的总时间/次数不用于计算加速比。
取样 PC 按 dylib 装载地址归一并对齐 ARM64 的 4 字节指令。原始 trace/XML/反汇编保留在本目录。
输入：{   "seed": 12345,   "bytes": 2097204,   "lines": 33904,   "sha256": "7bc5cf38f4e9a57f31d9ac4f36c672f082d6647b8843e43a9ccece83a18e3573" }
输入由 seed=12345 的确定性文本组成（2 MiB），此轮没有额外独立语料 holdout。

手工热点分析与实现
1. SHA256 基线 OpGroup2_EvIb 占 native 样本 34.58%，包含 subop/宽度/内存通路及标志计算。
   为 C1 寄存器立即数 ROL/ROR 增加 16/32 位、flags-live/dead 模板特化。NF 32-bit ROR 的反汇编主体为寄存器读取、ror、写回、尾跳。
   count 按 5 bit 屏蔽，16 位整圈旋转仍处理 CF；OF 只在 masked count=1 时定义；16 位高半寄存器与不受影响标志保留。
   新 profile 中 32-bit ROR NF 占 native 样本 12.43%。百分比的分母随优化变化，计时收益见下表。
2. SpecCriteria::Matches 已把 ModRM.mod 提取为 0..3；现有 SHL/SHR/SAR ModReg 和 ADD EAX 的注册仍用 0xC0/0xC0，无法匹配。修成 3/3，让现有特化真正启用。
3. 仅启用上述特化会改变 handler 指针，破坏旧精确融合模式。保留特化，在 2..4-op 序列生成器中对白名单语义家族做笛卡尔展开、全局去重。
   保留原先选中的 64 项及编号，追加 7 项，生成表共 71 项；新增融合体直接执行 ModReg/EAX 逻辑，原通用模式仍供内存等形式匹配。
   此轮修改的是当前默认扩展序列烘焙路径，未改旧的 pair-only legacy 生成路径。新增 ROTATE 模板目前没有对应入选融合模式。
   单测检查实际块入口：寄存器序列命中新四指令融合，内存序列仍命中原四指令融合；第三条指令 fault 后从故障指令恢复，不重复执行 SHR。
   gunzip 复采实际命中 SuperOpcode_4_066_...Shr_ModReg，约占 native 样本 4.71%。

后续有依据但未实现/未宣称收益的空间
- CoreMark：GCC 的 SHL/SAR/SHR 仍合计约 8% native；可进一步分离 opsize 和 flag liveness，保留 count=0 的标志语义，并同步展开融合家族。
- CoreMark Zig：Cmov_E_ModReg 约 4.72%，Movzx_Word 约 3.46%；可针对宽度/目的寄存器消除运行时分支，需独立 A/B。
- sort：Cmp_EbGb 约 10.20% 与 Jcc_E_Rel8 约 10.60%；检查寄存器/内存形式和短分支配对融合比单独扩展更多 MOV handler 更值得优先验证。
- grep regex：已有四指令融合占约 19.32%，通用 Cmp_EvGv_32 约 9.46%；先检查寻址/宽度变体的融合覆盖，避免扩大表却只迁移热点。
- tar：native 只有约 243ms，managed/I/O/进程开销显著；热项是解码与 SpecCriteria 匹配，不能用单指令优化推算整体加速。
