Bounded fusion / operand lowering / EAX-ESP pin

Build switches (CMake cache; independent at compile time)
  FIBERCPU_STATIC_SPECIALIZATION=ON/OFF
  FIBERCPU_ENABLE_DYNAMIC_SPECIALIZATION=ON/OFF
  FIBERCPU_ENABLE_LLVM_JIT=ON/OFF
  FIBERCPU_ENABLE_SUPEROPCODES=ON/OFF
  FIBERCPU_FUSION_STRATEGY=AUTO/BASE/EXTENDED/SHAPED
  FIBERCPU_OPERAND_SPECIALIZATION=AUTO/OFF/PROFILE/REGISTER/HYBRID
  FIBERCPU_OPERAND_BUDGET=AUTO or 0..1024
  FIBERCPU_OPERAND_SCOPE=AUTO/ALL/ADDED_FUSIONS
  FIBERCPU_GPR_PIN=AUTO/ON/OFF/ABI_ONLY/CONSERVATIVE/EAX_ESP/WRITE_BACK
  FIBERCPU_GPR_WRITE_BACK=ON/OFF (default ON)
  FIBERCPU_GPR_PIN_REGISTERS=EAX,ESP (any nonempty subset of the eight guest GPRs)
MSBuild forwards FusionStrategy, OperandSpecialization, OperandBudget,
OperandScope, GprPin, GprPinRegisters and GprWriteBack.

Ordinary builds, including static/NativeAOT and Wasm, default to SHAPED,
HYBRID/776, ALL, MEMORY and one shared operand plan. AUTO enables EAX/ESP
WRITE_BACK on ARM64 when Clang supports the required handler ABI. It leaves
pinning OFF on x64 and Wasm; x64 can still opt in with GPR_PIN=ON.
With pinning enabled by AUTO or ON, GPR_WRITE_BACK=OFF selects EAX_ESP
write-through. Turning pinning OFF does not change the shared operand plan.

Sequence training and custom fusion sources default to BASE, operand
lowering OFF and pin OFF. Explicit choices override AUTO. An existing
CMake cache with explicit pin or budget values retains those values.
Use AUTO to resolve them again.
An explicit generated fusion source overrides the source chosen by the
strategy. Set FIBERCPU_GENERATED_SUPEROPCODES_FILE to an empty value to
follow the selected strategy.

BASE is the reviewed GNU 64 patterns plus 7 semantic expansions. EXTENDED
adds 64 observed GCC CoreMark pairs and 32 four-op sequences (167 total).
Preserved BASE membership is baked into bit 0x40 of the match width;
handwritten rules use bit 0x80 and the low six bits hold the actual width.
SHAPED retains all BASE rules, but admits an added fusion only when an exact
operand clone covers its whole sequence. A miss continues matching shorter or
baseline rules. An added fusion cannot consume the head of a preserved fusion
whose tail extends beyond its own window. This prevents an added MOV/CMP pair
from splitting an existing CMP/Jcc pair; a four-op fusion may still subsume an
entire two-op comparison/branch. This limits the impact on operand paths outside the training
coverage; it never reverts a canonical instruction specialization.
Frozen manifests are checked in. Ordinary builds never execute a training guest.
PROFILE partially evaluates up to the configured budget in the selected plan.
The stock version 1 lists specialize ModRM, prefixes and effective-address
descriptors. Each clone uses the ordinary instruction logic, precise
fault/restart flow and constituent boundaries.
ADDED_FUSIONS instantiates only the fused shapes in that budget. The fusion
matcher returns their lowered entry directly. It
performs no separate per-instruction lowering pass or reverse normalization:
ordinary instructions retain canonical identity, and fused entries cannot be
constituents of these ordinary-logic-only patterns. This keeps cold decoder
paths out of the generic shape lookup and preserves existing ISA specialization.
ALL also lowers single instructions and maintains reverse identity on concat.
REGISTER lowers register-only forms to three destination classes: EAX, ESP,
other. Byte forms classify their parent register, so AH belongs to EAX; the
encoding for AH never refers to ESP. Read-only CMP/TEST has its own policy.
HYBRID first tries a bounded exact shape, then the general register class.

Order: decode -> liveness and canonical specialization -> canonical fusion ->
operand lowering. Only before concatenation, lowerings map back to their original
handler identity; then fusion and lowering run again. This preserves matching
without reverting an instruction specialization. The source generator remains
the authority for semantic specialization expansion.

Workload-specific decoded operand plans

Build the CLI with block profiling and run the workload with guest stats:

  dotnet build Podish.Cli/Podish.Cli.csproj -c Release -p:EnableBlockProfile=true
  dotnet Podish.Cli/bin/Release/net10.0/Podish.Cli.dll run --rm \
    --rootfs /path/to/rootfs --guest-stats-dir /tmp/guest-stats /path/to/guest

Export from the new guest stats directory or from BLK2 v3 dumps:

  python3 scripts/collect_operand_specializations.py /tmp/guest-stats \
    --output /tmp/operand-plan.json
  cmake -S libfibercpu -B build/operand-profile -DCMAKE_BUILD_TYPE=Release \
    -DFIBERCPU_OPERAND_PLAN_FILE=/tmp/operand-plan.json
  cmake --build build/operand-profile

Pass several profile paths to combine their counts. Each input can be a
blocks.bin file or its containing directory. Pass --fusions to the collector
when profiling with BASE or a custom generated fusion source. CMake also accepts
the plan through MSBuild's -p:OperandPlanFile=/tmp/operand-plan.json.

The version 3 plan saves all observed decoded shapes by default. --limit trims
the exported list. CMake's FIBERCPU_OPERAND_BUDGET controls how many rows become
handlers, up to 1024. Ranking starts with estimated dispatch count. Block entry
counts are estimates for constituent execution when a block can exit early.

Each match includes a catalog training ID, instruction length, ModRM
(also used for opcode-encoded registers), prefixes, decoder metadata, decoded
base/index/scale/segment, displacement and immediate. It guards every constituent
of a generated fusion. Addresses after relocation, resolved branch targets and
guest memory values are runtime inputs. Training and analysis require BLK2 v3.

A plan can also list scalar training IDs in base_displacement_ids. These
handlers share one baked address per base register and operand width. They
match 32-bit addresses with no index, segment override or immediate, keep the
displacement in the Op, and are selected after an exact operand match.
Recapture older profiles and regenerate their operand plans and fusion manifests.
Reviewed encoding-only plans use the same v3 IDs with "match": "encoding".
Their shape keys keep ModRM, prefixes and effective address encoding.
The BLK2 v3 training ID occupies the previous reserved word in each operation.
Scalar IDs come from catalog entries. Fusion IDs come from the ordered scalar
IDs and a generated or handwritten fusion tag. Embedded symbols remain
available for diagnostic block analysis.

Sequence profiles use schema 3 with numeric pairs and ngrams. Trained fusion
manifests use schema 3 and store numeric pairs or sequences. The operations dictionary resolves
IDs to catalog identifiers for code generation.

Dynamic operand templates

Capture BLK2 v3 profiles from several workloads using the same instruction
and fusion catalog. The collector's default exports every recognized shape:

  python3 scripts/collect_operand_specializations.py /tmp/coremark-stats \
    /tmp/gzip-stats /tmp/sha256-stats --output /tmp/dynamic-operands.json
  cmake -S libfibercpu -B build/dynamic-operands -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_CXX_COMPILER=/path/to/llvm/bin/clang++ \
    -DLLVM_DIR=/path/to/llvm/lib/cmake/llvm \
    -DFIBERCPU_DYNAMIC_OPERAND_PLAN_FILE=/tmp/dynamic-operands.json
  cmake --build build/dynamic-operands --parallel

For the managed CLI build, pass -p:DynamicOperandPlanFile=/tmp/dynamic-operands.json
with NativeClangDir and LlvmConfigDir set for the matching toolchain.
The backend targets native macOS arm64 and uses the build's handler ABI,
including register pins. Both dynamic operand templates and the online block
JIT use the same catalog operation rules and Clang bitcode. The build tool
binds each recorded operand shape, inlines the selected operations into a
threaded handler, then has LLVM optimize and emit an ARM64 object. The
interpreter can materialize the resulting machine-code templates with online
JIT off and without LLVM libraries at runtime. The compiler and build tool
require matching upstream Clang and LLVM major versions (21 or newer).

The dynamic plan is independent of the static operand budget.
FIBERCPU_STATIC_SPECIALIZATION=OFF disables ISA optimizations, native operand
clones and precompiled fusions. Scalar plans can still produce dynamic
handlers. A fusion recipe uses the LLVM kernels for its constituent
instructions and is selected when the corresponding fusion is enabled.
FIBERCPU_DYNAMIC_SPECIALIZATION=0 disables runtime materialization.

The packer groups LLVM machine code by handler identity and fixed
instruction bits. A template stores one text image and the positions and
masks of varying immediate fields. The packer verifies that patching each
recipe reconstructs the text bytes. It keeps outlined functions with the
entry point and resolves branches within the image. External branches
use local veneers. Constant and GOT references are relocated into a pool
beside the code. Unsupported relocations or operand forms keep the ordinary
lowering path. Coverage, exclusion reasons and code sizes are written to
generated/dynamic_operands/report.json.

At block decode, a full operand-key match materializes a recipe on first use
in an executable arena and reuses the resulting handler on subsequent decodes.
An unseen key or an unavailable arena uses the existing handlers. Training
counts are block-based estimates. Materialized handlers have individual reflection names and IDs. Their names
retain the original logic identity for the profile collector.

Experimental LLVM block JIT

Configure with FIBERCPU_ENABLE_LLVM_JIT=ON and LLVM_DIR pointing to LLVM's
CMake package. Use a native macOS arm64 build with matching upstream Clang
and LLVM major versions, at least LLVM 21. Select a deployment target
supported by the installed LLVM library. The build packages Clang bitcode
for the generic logic and parameterized templates selected in the catalog.

Launch with FIBERCPU_LLVM_JIT=1 to bind decoded operands in the IR, or
FIBERCPU_LLVM_JIT=generic to exercise the generic IR. Set it to 0 or omit it
to use ordinary block entry points. The runtime switches are read from the
host environment on first use. They are independent of the build switches.

The compiler patches the decoded operand fields and immediate on each call
site in the block template, then explicitly inlines the opcode IR before
running the block optimization pipeline. It covers up to 64 decoded slots,
including selected scalar memory operations and direct branches. The compiled
entry tail-dispatches at the first unsupported slot or the block sentinel.
LLVM ORC compiles and relocates the resulting handler.

The decoded slots retain their scalar handler pointers. A memory restart
re-enters the original slot through the existing slow path. A completed
write resumes at the following slot. The block's entry alone points to JIT
code.

The MMU code cache owns the ORC resource leases. An invalidated block keeps
its lease while the decoded storage remains reachable or can be revalidated.
A quiescent cache reset releases the leases together with the decoded storage.
Identical sequences can share a lease across caches while blocks still refer
to it. The process allows up to 128 live sequences. X86_GetLLVMJitBlockCount
reports cumulative materializations and X86_GetLLVMJitLiveBlockCount reports
the currently owned executable sequences.

Pin appends one uint32 argument per selected GPR to the preserve_none handler
signature. CMake generates the register IDs, parameter order, lookup conditions
and slot mapping. It accepts comma- or semicolon-separated x86 register names
in any case, rejects duplicates, and normalizes their order to EAX, ECX, EDX,
EBX, ESP, EBP, ESI, EDI. One native library has one signature across all handlers,
sentinels, branch links, restart/retry, Step/Run and reflection. The resolved
optimization configuration reports the actual list as pins=.

Examples: -DFIBERCPU_GPR_PIN_REGISTERS=ECX,EDI with CMake or
-p:GprPinRegisters=ECX%2CEDI on the dotnet command line. Choose GprPin=OFF to
turn pin off. EAX_ESP is the legacy name for the static-write-through mode.
The selected register list applies to all pin modes.

The full frozen shape plan and extended pin classification apply to the
verified EAX,ESP list. Other lists select BASE fusion with zero exact shape
budget and only the basic ModRM MOV, integer ALU, CMP and TEST pin classification.
The normal ISA handlers and their existing specializations still apply.
A pin-specific destination class is instantiated only when its parent GPR is
in the current list. Byte forms use the parent of AL/AH, CL/CH, DL/DH or BL/BH.
Custom lists are usable but have no measured throughput guarantee.
ABI_ONLY isolates the signature cost. CONSERVATIVE caches reads and reloads
all selected values at ordinary tails. EAX_ESP uses decoded static write classes to
forward unchanged values. Both write-through modes update the canonical register
file on every write. PIN_ASSUME expresses equality on entry so LLVM can replace
some register-file loads with the threaded values.

WRITE_BACK makes the selected threaded values authoritative inside the handler
chain. GprCache reads and writes through references to the current handler
arguments. This includes partial register writes and address base/index reads.
A pinned write skips ctx.regs. Dynamically selected reads can use csel on ARM64.
Writes select the pin value or branch to a guarded register-file store.
Compile-time operand facts eliminate these choices for known registers.

Ordinary tails, fused constituents and chained blocks forward the live values.
Host exits and memory restart/retry publish all selected pins. Blocking TLB hits
stay in the chain. Blocking misses and explicit callbacks publish the pins before
the observer runs, then reload them before resuming. There is no dirty bit.

GPR pin requires Clang support for the native preserve_none tail-call ABI.
Remeasure after a compiler upgrade: preserve_none is an unstable compiler ABI.
The public C ABI is unchanged. BuildFeatures bits 4..5 identify operand mode,
bits 8..9 hold the low pin mode bits, and bit 11 holds the high bit (WRITE_BACK).
Bit 10 identifies ADDED_FUSIONS scope. X86_GetOptimizationConfig returns strategy, enabled
state, operand mode/budget, pin mode and the frozen shape-plan hash. The existing
superopcode set hash identifies the selected generated fusion source.

Validation methodology
Use the existing GCC 15.2 -O2 i386 CoreMark ELF only, SHA256
48c3ecf2c2e2bbbebc8249f3f2ab30933a1e85e8eeaa1b6c0806bed90a5085db.
Keep rootfs, managed CLI and arguments identical. Fixed 60000 iterations,
0x0 0x0 0x66 60000 7 1 2000; require CRC and >=10 seconds.
GNU holdout: gzip, gunzip, sed, fixed/regex grep, sort, SHA256, tar, using a
fresh deterministic seed 987654 fixture. Validate every output, including
archive members/decompressed bytes. Build all variants and finish tests before
serial timing. Rotate variant order between rounds. Record individual changes;
a geomean cannot establish the absence of regressions.
A finite corpus cannot prove non-regression for all possible guests. Promotion
requires no repeatable regression on the measured paths, with explicit bounds.

GNU pin coverage experiment (448-entry comparison plan)
  FIBERCPU_PIN_SPECIALIZATION=AUTO|BASE|SCALAR|MEMORY
  FIBERCPU_OPERAND_PLAN_FILE=<absolute frozen JSON path>
  FIBERCPU_OPERAND_BUDGET=AUTO or 0..1024
MSBuild equivalents: PinSpecialization, OperandPlanFile, OperandBudget.
The reviewed operand-shapes-gnu-v1.json preserves all 256 GCC entries, then
adds 64 GNU fused and 128 GNU scalar shapes. Use HYBRID/ALL, budget 512;
compare pin OFF and EAX_ESP with identical remaining switches. SCALAR adds
opcode-register MOV/INC/DEC/BSWAP, LEA and Jcc write classification. MEMORY
additionally classifies exact integer ALU/test/cmp/MOV/MOVZX/MOVSX memory
forms. Only normal Continue tails use their known write sets. Nonblocking
MMU misses go through Restart/Retry with pin reloads; slow callbacks, branch
exits, opaque/string/stack kernels keep their conservative behavior. Guest
backing storage must be separate from the emulator's own architectural state.
No guest addresses, immediates, displacements or data values enter this plan.
The plan can be extended with extend_operand_plan.py from one decoded v3
operand plan per workload. The tool aggregates dispatch counts by encoding. Scores normalize each workload before ranking,
so the longest workload does not consume the entire shape budget. Appending
entries preserves the existing GCC priorities and bounded fusion admission.

GNU write-back profile
The production preset uses operand-shapes-gnu-writeback-v1.json
with SHAPED, HYBRID, ALL, budget 776 and MEMORY pin specialization. The first 704
entries preserve the original GNU write-back plan, which appended 48 fused and
208 single-instruction shapes to the earlier 448-entry GNU plan. Entries
705–776 cover the 32-bit GCC 13 CoreMark workload; see coremark-gcc13-coverage.txt.
Budget 704 selects the original GNU write-back prefix for comparisons.
Both base and index fields are decoded facts. No guest values or relative
displacements are fixed by this plan. The original plan remains selectable.

In ALL scope, the fusion lookup and operand lowering run in a single forward
pass. A matcher reads only its current instruction and successors. For
concatenated blocks, the decoded metadata marks the entries that were lowered
so reconstruction only reverse-maps those entries before matching again.
The metadata bit does not change the decoded record size.

To extend a reviewed encoding-only plan, pass it as --base and pass each
newly captured decoded v3 plan as a separate --counts argument.
The archived experiment inputs and timings record the original measurement.
